# AI PR Review 报告模块详解

本文档详细介绍 AI PR Review 分析报告中的全部 9 个模块，涵盖每个模块的展示内容、数据来源、生成逻辑和设计意图。

---

## 模块全景图

```
┌─────────────────────────────────────────────┐
│  📋 摘要面板                                 │
│  PR身份 | 变更摘要 | 指标 | 来源 | 评审重点    │
├─────────────────────────────────────────────┤
│  📊 上下文覆盖面板                           │
│  目标文件 | 测试检查 | 仓库文档 | 相似PR/Issue │
├─────────────────────────────────────────────┤
│  📦 PR 准备面板                              │
│  建议标题 | 类型 | 标签 | Walkthrough |       │
│  Changelog | PR描述草稿                      │
├─────────────────────────────────────────────┤
│  ⚠️ 风险概览                                │
│  文件级风险评分 + 审查维度标注                │
├─────────────────────────────────────────────┤
│  🛡️ 评审问题                                │
│  代码行级具体缺陷发现                         │
├─────────────────────────────────────────────┤
│  🧪 测试建议                                │
│  测试缺口分析与用例建议                       │
├─────────────────────────────────────────────┤
│  💡 改进建议                                │
│  代码改进 + 文档补充（非阻塞）                │
├─────────────────────────────────────────────┤
│  📝 GitHub 评论预览                          │
│  最终 Markdown 输出预览                      │
├─────────────────────────────────────────────┤
│  💬 追问与交互                               │
│  追问 / 修代码 / 写测试 三模式对话            │
└─────────────────────────────────────────────┘
```

9 个模块按功能分为三组：

| 组 | 模块 | 核心价值 |
|-----|------|---------|
| **理解 PR** | 摘要、上下文覆盖 | 快速搞懂这个 PR 是干什么的 |
| **发现问题** | 风险概览、评审问题、测试建议 | 找出代码里有什么毛病 |
| **完善 PR** | PR 准备、改进建议、评论预览、追问交互 | 把 PR 收拾好，把问题讨论清楚 |

---

## 1. 摘要面板

### 定位

报告的"封面"，承载最核心的一眼看懂信息。始终可见。

### 展示内容

| 元素 | 数据来源 | 说明 |
|------|---------|------|
| PR 身份行 | `pr.owner/repo#number` | 形如 `maluQxzh/AI-PR-Review#42`，可点击跳转 GitHub |
| PR 标题 | `pr.title` | PR 的原标题 |
| 变更摘要 | `summary.what_changed` | 一句话描述这个 PR 做了什么 |
| 三项指标 | 统计值 | 问题数量、高风险文件数、测试建议数 |
| 分析来源徽章 | `analysis_source` | 🟢 LLM API / 🟡 快速重试 / 🔴 降级回退 / 🔵 演示数据 |
| 分析详情 | `analysis_detail` | 补充说明，如使用的模型、降级原因、分析耗时 |
| 评审重点标签云 | `summary.review_focus` | 中文标签（如"安全审查""数据正确性""并发安全"），指导 reviewer 重点关注哪些方面 |

### 它回答的问题

**"这个 PR 是什么、改了什么、严不严重、从哪看起？"**

## 2. 上下文覆盖面板

### 定位

展示分析引擎在审查代码时参考了多少背景信息，帮助评估审查结论的可靠性。仅在配置了 `GITHUB_TOKEN` 时显示。

### 核心指标

| 指标 | 说明 |
|------|------|
| 目标文件数 | 有多少个变更文件被纳入了上下文收集范围 |
| 有上下文的文件数 | 其中多少文件成功获取到了额外背景 |
| 历史搜索条目数 | 从 GitHub Issues / PRs 中搜到了多少条相关历史记录 |

### 子列表

#### 相关测试

列出分析器检查过的测试文件。分析器通过命名约定启发式来猜测测试文件与源文件的对应关系：

| 语言 | 匹配模式 |
|------|---------|
| Python | `test_*.py` / `*_test.py` 对应 `src/*.py` |
| JavaScript/TypeScript | `*.test.ts` / `*.spec.ts` 对应 `src/*.ts` |
| Go | `*_test.go` 对应 `*.go` |
| Rust | `tests/*.rs` 对应 `src/*.rs` |

如果对应的测试文件不存在，这里会标注测试缺失，并触发风险分数的"测试缺口惩罚"（+12 分）。

#### 仓库约定

列出分析器读取的仓库文档：

- `.ai-review.yml` — 仓库的自定义审查配置
- `README.md` — 项目说明
- 依赖清单（`package.json`、`pyproject.toml`、`Cargo.toml` 等）
- CI 配置（`.github/workflows/` 等）

#### 降级说明

上下文收集过程中遇到的问题：

- "GitHub Token 未配置，跳过历史搜索"
- "目标文件超过上限，仅处理前 N 个"
- "仓库文档未找到"

### 嵌入子区域：相似 Issue / PR

从 GitHub 历史中搜索出和当前 PR 相似的 Issues 和 PRs。每个条目显示：

| 字段 | 说明 |
|------|------|
| 标题 | 可点击跳转到 GitHub |
| 状态 | open / closed / merged |
| 类型 | issue / pull_request |
| 相关性说明 | 为什么觉得它和这个 PR 有关（按标题关键词 + 文件路径关键词搜索匹配） |

上限 6 个条目，由 `MAX_CONTEXT_HISTORY_ITEMS` 配置控制。

### 它回答的问题

**"AI 做判断时看了多少东西？它的结论有没有充分的信息基础？我是不是该信任它的判断？"**

如果上下文覆盖很薄（比如没读到测试文件、没历史记录），审查结论的可靠性就要打折扣。

## 3. PR 准备面板

### 定位

帮 PR 作者把 PR 本身收拾得更专业。内容完全是**非阻塞性的**，不挑代码毛病，而是提供实用的 PR 辅助产物。

### 展示内容

| 元素 | 说明 | 示例 |
|------|------|------|
| **建议标题** | AI 根据 diff 内容重新拟定的 PR 标题 | `fix: 支付授权默认拒绝策略` |
| **PR 类型** | AI 推断的 PR 类型徽章 | `bugfix` / `feature` / `refactor` / `docs` / `test` / `chore` / `security` / `performance` |
| **标签** | AI 建议打的 GitHub Labels，每个标签带理由和置信度 | `breaking-change`（置信度 0.85，原因：修改了函数签名） |
| **Walkthrough** | 按功能区域分组的变更走读 | "支付授权模块：将默认行为从隐式允许改为显式拒绝" |
| **Changelog** | 一句话 changelog 条目 | "支付写入采用 deny-by-default 策略" |
| **PR 描述草稿** | 完整 Markdown PR 描述，包含 6 个章节 | Summary / Walkthrough / Testing / Risks / Rollback / Review Notes |

### PR 描述草稿结构

```
## Summary          — 变更摘要
## Walkthrough      — 按区域走读
## Testing          — 测试策略建议
## Risks / Rollback — 风险与回滚计划
## Review Notes     — 建议标题、类型、标签
```

每个区块都自带"复制"按钮。

### 它与改进建议的区别

| | PR 准备 | 改进建议 |
|------|---------|---------|
| 关注点 | PR 的**元信息和描述** | 代码本身的**质量提升** |
| 受益者 | Reviewer（更好理解 PR） | 开发者（改进代码写法） |
| 产物 | 标题、标签、描述、Changelog | 重构建议、文档补充 |

### 它回答的问题

**"如果我要把这个 PR 发出去，标题怎么起、标签怎么打、描述怎么写、changelog 怎么填才能让 reviewer 快速理解？"**

## 4. 风险概览

### 定位

**文件级别**的预筛选机制。不对具体 bug 下结论，而是回答：**"这个 PR 改的文件里，哪些文件一旦出问题后果最严重？"**

### 风险分数计算

每个变更文件被打 0-100 的**风险分数**，分四档：

| 级别 | 分数 | 含义 |
|------|------|------|
| 🔴 Critical | ≥ 85 | 触及核心安全/数据逻辑，出问题就是事故 |
| 🟠 High | ≥ 65 | 风险较高，需要重点审查 |
| 🟡 Medium | ≥ 35 | 有一定风险 |
| 🟢 Low | < 35 | 低风险，改动小且不敏感 |

### 计分规则

分数在 `risk_classifier.py` 中计算，综合以下信号：

#### 路径关键词 (+18)

文件名包含以下敏感词则加分：

| 关键词 | 涉及领域 |
|--------|---------|
| `auth` | 认证或授权 |
| `permission` | 权限逻辑 |
| `payment` | 支付代码 |
| `migration` | 数据库迁移 |
| `security` | 安全敏感代码 |
| `crypto` | 加密代码 |
| `database` | 数据库代码 |
| `config` | 运行时配置 |

#### 代码模式 (+8 ~ +18)

用正则扫描 diff 内容：

| 正则模式 | 含义 | 权重 |
|---------|------|------|
| SQL 关键字 | 新增了数据库查询逻辑 | +14 |
| 访问控制关键词 | 修改了权限校验代码 | +18 |
| 异常/错误处理词 | 修改了错误处理行为 | +10 |
| HTTP 客户端词 | 新增了网络请求行为 | +10 |
| TODO/FIXME 标记 | 包含临时实现标记 | +8 |
| 提前 return | 新增了宽松的提前退出分支 | +12 |
| 异步/并发关键词 | 涉及并发或异步逻辑 | +10 |
| 弃用标记 | 涉及废弃 API 或兼容性变更 | +8 |
| 阻塞/查询关键词 | 潜在性能问题 | +10 |

#### 规模与缺失信号

| 信号 | 加分 |
|------|------|
| 改动 ≥ 120 行 | +15 |
| 改动 ≥ 40 行 | +8 |
| PR 中没有测试文件被修改 | +12 |
| 文件是配置文件（`.json`, `.yml`, `.yaml`, `.toml`） | +6 |

分数封顶 100，下限 0。

### 审查维度标注

每个文件会被打上维度标签，告诉审查者从哪个角度去看：

| 维度 | 含义 | 检测关键词 |
|------|------|-----------|
| `security` | 安全审查 | auth, permission, encrypt, injection, os command, serialize |
| `logic` | 逻辑正确性 | null, condition, boundary, edge case |
| `concurrency` | 并发安全 | async/await, thread, lock, channel |
| `compatibility` | 兼容性 | deprecated, version, package manifest |
| `performance` | 性能 | sleep, N+1 query, loop map/filter |
| `maintainability` | 可维护性 | TODO/FIXME, unwrap/expect/panic |
| `data` | 数据正确性 | SQL, migration, schema change |
| `test_gap` | 测试覆盖缺口 | 无测试文件变更时合成 |

### 它回答的问题

**"这个 PR 里哪些文件最危险，应该从哪个角度审查？"** — 帮 reviewer 把有限的注意力分配到最值得看的地方。

## 5. 评审问题

### 定位

**代码行级别**的具体缺陷发现。直接指出：**"这一行代码有什么问题，影响是什么，该怎么修。"**

### Finding 数据结构

| 字段 | 类型 | 含义 |
|------|------|------|
| `title` | string | 问题的中文描述 |
| `severity` | P0-P3 | 严重级别 |
| `confidence` | 0-1 float | 有多确定这是个真问题 |
| `category` | string | 问题类别 |
| `file` | string | 文件路径 |
| `line` | int | 变更行号 |
| `evidence` | string | 为什么认为这是个问题 |
| `impact` | string | 不修的后果 |
| `suggestion` | string | 怎么修 |
| `comment_draft` | string | PR 评论草稿 |
| `tag` | string | 降级时标记为 `[建议]` |

### 严重级别

| 级别 | 含义 | 典型问题 | 置信度范围 |
|------|------|---------|-----------|
| **P0** | 致命 | 硬编码密钥/密码、远程代码执行（RCE） | ≥ 0.88 |
| **P1** | 高危 | SQL 注入、XSS、`eval()`/`exec()` 动态执行、认证绕过 | 0.72-0.82 |
| **P2** | 中危 | 逻辑错误（空值/边界）、资源泄漏、可变默认参数、宽松异常捕获 | 0.65-0.72 |
| **P3** | 低危/建议 | 可维护性问题（TODO/FIXME、console.log、魔法数字）、纯风格问题 | 0.60-0.72 |

### 类别

| 类别 | 典型检测内容 |
|------|------------|
| `security` | 注入、认证绕过、敏感数据暴露、不安全反序列化、加密误用 |
| `logic` | 空值/边界条件、错误条件判断、类型错误 |
| `concurrency` | 竞态条件、缺失事务、死锁风险、异步陷阱 |
| `compatibility` | 破坏性 API 变更、废弃 API 使用、版本冲突 |
| `performance` | N+1 查询、内存问题、阻塞操作、低效算法 |
| `maintainability` | 错误被吞没、魔法数字、TODO/FIXME、过深嵌套 |
| `data` | 数据库正确性问题 |

### 发现路径

#### 路径 A：LLM 深度审查（有 API Key 时）

将 PR diff 和上下文发给大模型，按 6 个维度系统审查。系统提示要求：

- Fast 模式：仅报告 P0/P1，最多 5 个 finding，目标文件 0 个
- Standard 模式：审查 Top 5 高风险文件
- Deep 模式：审查 Top 15 文件 + 二次校验，最多 15 个 finding

LLM 被要求输出结构化 JSON，每个 finding 必须有证据支撑、影响描述和可操作建议。

#### 路径 B：模式分析器（无 API Key 时的启发式降级）

用 **49 条正则规则**做静态模式匹配，按语言覆盖：

| 语言 | 规则数 | 典型检测项 |
|------|--------|-----------|
| Python | 11 | 裸 `except:`、可变默认参数、`eval`/`exec`、`open()` 无 `with`、`os.system`、`pickle.load`、`yaml.load`、硬编码密钥、生产环境 `assert`、阻塞 `sleep`、`dict.get` 未检查 |
| JS/TS | 12 | `==` 宽松相等、`innerHTML`、`eval`、`document.write`、`new Function()`、`setTimeout` 字符串、`dangerouslySetInnerHTML`、SQL 拼接、`map()` 缺 key、`localStorage` 存敏感数据 |
| Go | 7 | 未检查 error、循环中 `defer`、`panic`、硬编码密钥、阻塞 sleep、SQL 拼接、nil 解引用 |
| Java | 8 | 空 catch、`System.out`、循环字符串 `+` 拼接、JDBC 泄漏、`==` 比较字符串、`Runtime.exec` |
| Rust | 5 | `unwrap`、空 `expect`、`unsafe` 块、`panic`、循环 `clone` |
| 跨语言 | 6 | TODO/FIXME、硬编码密钥（通用正则）、SQL 注入拼接、路径遍历、命令注入、链式调用空值 |

### 验证流水线

Finding 在进入报告前经过多步后处理，过滤假阳性：

1. **文件过滤** — 移除文件不在变更集中的 finding
2. **行号校验** — 行号必须在新增/修改的 hunk 内
3. **证据交叉验证** — 证据关键词必须在 diff（±5 行内）中找到匹配
4. **风格降级** — 纯风格问题降为 P3 + `[建议]` 标签
5. **上下文降级** — 文档文件、已删除文件、微小变更中的 finding 做降级处理
6. **置信度调整** — 基于测试覆盖率微调（有测试变更 -5%，高风险文件无测试 +8%）
7. **最低阈值截断** — 置信度 < 0.55 的丢弃
8. **去重** — 精确去重 + 三元组 Jaccard 语义去重（阈值 0.75）

### 它回答的问题

**"这个 PR 具体有什么 bug？严重吗？怎么修？"**

## 6. 测试建议

### 定位

回答核心问题：**"这个 PR 改了行为，但测试覆盖有缺口，具体应该补哪些测试用例？"**

### 数据结构

| 字段 | 含义 | 示例 |
|------|------|------|
| `title` | 一句话概括要补什么测试 | "补充支付授权回归测试" |
| `reason` | 为什么需要这个测试 | "这个 PR 修改了支付代码中的访问控制逻辑" |
| `suggested_case` | 具体的测试用例建议 | "断言缺少角色会被拒绝，且用户必须具备 payment:write 权限" |

### 生成逻辑

#### LLM 路径（有 API Key 时）

LLM 结合它发现的代码问题推断测试缺口：
- 发现支付授权逻辑改了 → 建议补授权相关的回归测试
- 发现新增了 SQL 查询 → 建议补正常输入/空输入/SQL 恶意输入的测试
- 发现改了错误处理路径 → 建议补成功路径 + 失败路径 + 边界值

#### 启发式降级路径（无 API Key 时）

生成两条通用建议：
1. **"为最高风险文件补充回归测试"** — 覆盖成功路径、失败路径、边界值
2. **"使用 dry-run 验证 GitHub 评论预览"** — 工具自身的使用建议

### 主要针对的测试缺口

| 缺口类型 | 典型场景 |
|----------|---------|
| **安全边界测试缺失** | 改了权限/认证逻辑，但没有测"无权限时被拒绝" |
| **输入校验测试缺失** | 新增了接收外部输入的代码，但没有测恶意输入/空值/边界值 |
| **回归测试缺失** | 改了核心业务逻辑，但没有对应的回归用例 |
| **错误路径测试缺失** | 加了新的错误处理分支，但只测了成功路径 |
| **高风险文件无测试变更** | 改了高风险文件但 PR 里没有任何测试文件被修改 |

### 它回答的问题

**"测够了没？不够的话，具体应该补什么测试？"**

## 7. 改进建议

### 定位

回答核心问题：**"功能上没问题，但从代码质量角度看，有哪些可以做得更好的地方？"**

定位是**非阻塞性的** — 不会阻止 PR 合并，只是帮开发者把代码质量再提一个台阶。

### 两种类型

#### 代码改进 (`CodeImprovement`)

| 字段 | 含义 | 示例 |
|------|------|------|
| `title` | 简短标题 | "把授权默认值改成显式拒绝" |
| `file` + `line` | 具体位置 | `src/payment/authorize.ts:22` |
| `category` | 改进类别 | maintainability / testability / reviewability / performance |
| `reason` | 为什么改 | "支付授权逻辑的默认分支影响安全边界" |
| `suggestion` | 怎么改 | "把缺少角色的路径命名为 deny-by-default" |
| `confidence` | 置信度 | 0.65-0.7 |

#### 文档建议 (`DocumentationSuggestion`)

| 字段 | 含义 | 示例 |
|------|------|------|
| `target` | 应该更新的文档 | `docs/security.md` |
| `reason` | 为什么需要更新 | "支付权限边界发生变化" |
| `proposed_text` | 建议添加的内容 | "支付写入必须采用 deny-by-default 策略……" |

### 改进类别及对应的问题

| 类别 | 针对什么问题 | 典型建议 |
|------|-------------|---------|
| **maintainability** | 逻辑能工作但难懂/难改 | "封装参数校验逻辑"、"提取重复的判断条件" |
| **testability** | 行为难以验证 | "把核心逻辑抽成可单独测试的函数" |
| **reviewability** | Reviewer 看不懂这个 PR 在干什么 | "在 PR 描述里说明预期行为和验证路径" |
| **performance** | 能工作但有效率隐患 | "避免在循环里重复创建对象"、"批量查询代替逐条查询" |

### 生成逻辑

#### LLM 路径

LLM 输出 `generated_artifacts`，包含 `code_improvements`（最多 5 个）和 `documentation_suggestions`（最多 3 个）。

#### 启发式降级路径

基于风险维度和分数生成模板化建议：

1. 文件有 `maintainability` 维度 → 建议"简化被修改的路径"
2. 文件有 `test_gap` 维度 → 建议"让变更行为更容易验证"
3. 文件风险分 ≥ 60 → 建议"给高风险变更加 reviewer 注释"
4. PR 改了行为但没改文档 → 建议更新 `docs/api.md` 或 `README.md`

上限 6 个代码改进。

### 合并补充逻辑

`coerce_generated_artifacts` 函数负责合并 LLM 产出和降级产出 —— LLM 可能只返回了部分产物，缺失的部分由降级路径补充，保证**无论如何都能产出改进建议**。

### 它与 PR 准备面板的区别

| | PR 准备 | 改进建议 |
|------|---------|---------|
| 关注点 | PR 的**元信息和描述** | 代码本身的**质量提升** |
| 受益者 | Reviewer（更好理解 PR） | 开发者（改进代码写法） |
| 产物 | 标题、类型、标签、Walkthrough、Changelog、PR 描述 | 代码重构建议、文档补充建议 |

### 它回答的问题

**"代码能工作，但能写得更好吗？有什么文档该一起更新？"**

## 9. 追问与交互

### 定位

整个报告里**唯一有交互能力**的部分。不满足于静态审查结果，可以继续和 AI 讨论这个 PR。

### 三种模式

| 模式 | 图标 | 说明 | 系统 Prompt 特点 |
|------|------|------|-----------------|
| **追问** | 💬 | 针对审查结果继续提问 | 知道审查结果上下文，可引用具体 finding 和文件 |
| **修代码** | 🔧 | 针对某个 finding 给出修复代码 | 输出完整 diff/patch，保持项目代码风格 |
| **写测试** | 🧪 | 为某段变更生成测试用例 | 输出完整测试代码，覆盖成功/失败/边界路径 |

### 交互能力

| 能力 | 说明 |
|------|------|
| **对话历史** | 所有问答保留在对话中，支持多轮追问，历史持久化到数据库 |
| **建议问题** | AI 根据审查结果自动生成推荐问题，点击即可提问 |
| **图片支持** | 追问时可附带截图，自动切换到多模态模型处理 |
| **上下文感知** | 知道当前 PR 的审查结果、finding 列表、文件风险信息 |

### 它回答的问题

**"我对审查结果有疑问怎么办？"**

不需要切到 ChatGPT，直接在报告里：
- 追问："第二个 finding 能详细解释吗？"
- 要修复代码："针对 P1 的 SQL 注入问题给个修复 patch"
- 要测试用例："给支付授权模块生成单元测试"

形成一个完整的**审查 → 讨论 → 修复**闭环。

## 附录：三条降级路径

系统设计原则：**在任何情况下都能生成有用的报告**，即使没有任何外部凭证。

| 层级 | 条件 | 行为 |
|------|------|------|
| **完整 LLM** | `GITHUB_TOKEN` + `LLM_API_KEY` 均已配置 | 完整 AI 审查，所有模块均由 LLM 驱动 |
| **仅模式分析** | `GITHUB_TOKEN` 已配置，无 `LLM_API_KEY` | GitHub 数据可用，模式分析器 49 条规则产出 finding，风险分类和降级产物正常工作 |
| **离线演示** | 无任何凭证 | 前端点击"加载演示"，加载静态 `demoReport.ts` 数据，所有模块展示示例内容 |
